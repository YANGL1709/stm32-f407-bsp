# 从 `while` 到 1ms 中断：一个按键为什么要走这么远

> 一句话结论：**按键的难点不在"读引脚"，在"时间归谁管"。**
> 阻塞版把时间交给了 CPI 空转，轮询版把时间交给了主循环跑多快，只有中断版把时间交回给硬件。

---

## 1. 阻塞版：`while` 等松手，为什么卡死

最初的写法大概是这样的：

```c
void Key_Scan(void)
{
    if ((KEY_PORT->IDR & (1U << KEY_PIN)) == 0)     /* 检测到按下 */
    {
        HAL_Delay(20);                              /* 消抖 */

        while ((KEY_PORT->IDR & (1U << KEY_PIN)) == 0)
            ;                                       /* 等松手 */

        /* 松手了，处理按键 */
    }
}
```

跑起来是能用的——按一下亮灯，再按一下灭灯。

**问题在现场：按住不放，整个程序就停在那里。**

不是"按键不响应"，是**主循环再也回不去了**。所有其他事情——闪烁的 LED、要收的串口数据、要打印的日志——全部停下来。

### 三处阻塞

| 位置 | 阻塞多久 |
|---|---|
| `HAL_Delay(20)` | 固定 20ms |
| `while` 等松手 | **取决于人手按多久**（按 3 秒就卡 3 秒） |
| 之后的处理 | 未知 |

第二行最要命，因为它的时长**由用户决定**，不是由代码决定。

### 根因

这个结构的本质是：**用 CPU 空转来"等待时间流逝"。**

CPU 明明可以在这段时间里去干别的事，却被一行 `while` 钉死在这里。
换句话说——**时间是主循环的敌人，不是它的资源。**

---

## 2. 轮询版：主循环 10ms 采样，节拍为什么不可靠

第一步改进是把状态机搬到主循环里，靠计次来分频：

```c
void Key_Tick(void)
{
    static uint8_t Count;
    ...
    Count++;
    if (Count >= 20)        /* 想表达"每 20 个单位采样一次" */
    {
        Count = 0;
        /* 采样 + 状态机 */
    }
}
```

```c
while (1)
{
    Key_Tick();             /* 主循环每转一圈调一次 */
    /* 其他业务 */
}
```

看起来"不阻塞"了。**但节拍是假的。**

### 问题：`Count` 数的是次数，不是时间

| 主循环这一圈干了什么 | 一圈耗时 | "20 次调用"实际是 |
|---|---|---|
| 只有几个 if | ~1μs | 20μs ← 采样快得离谱，抖动完全没滤掉 |
| 加了 `printf` | ~500μs | 10ms |
| 加了 Flash 擦除 | ~20ms | **400ms** ← 按键完全没反应 |
| 某次进了死循环 | ∞ | 永远不采样 |

**同一个 `Count >= 20`，在不同的主循环里代表完全不同的时间。**

### 根因

**把"时间"用"循环次数"来表达。** 循环次数不是时间，它只是时间的一个不确定函数。

只要主循环里任何一处变慢（加打印、加延时、加一次 Flash 操作），按键的消抖窗口就跟着变——而消抖窗口是不能变的，它由**机械特性**决定，不由你的代码决定。

> 这里有个更普遍的规律：**任何"靠循环次数计时"的代码，都会在系统变复杂之后悄悄失效。**

## 3. 中断版：TIM2 1ms → 20ms 采样 → 状态机

最终方案把时基交给硬件：

```
系统时钟 168MHz
   └─ APB1 = 168/4 = 42MHz        （分频≠1，所以定时器时钟 ×2）
        └─ TIM2 时钟 = 84MHz
             ├─ PSC = 84 - 1  → 计数频率 1MHz（1 个计数 = 1μs）
             └─ ARR = 1000 - 1 → 每 1000 个计数溢出一次 = 1ms
```

```c
void Bsp_Tim_Init(void)
{
    RCC->APB1ENR |= (1U << 0);

    TIM2->CR1 = 0;
    TIM2->PSC = 84 - 1;
    TIM2->ARR = 1000 - 1;
    TIM2->EGR = TIM_EGR_UG;        /* 立即装载 PSC/ARR */
    TIM2->SR  = ~TIM_SR_UIF;       /* SR 是写 0 清除 */

    TIM2->DIER |= TIM_DIER_UIE;    /* ① 外设级使能 */
    NVIC_SetPriority(TIM2_IRQn, 5);
    NVIC_EnableIRQ(TIM2_IRQn);     /* ② NVIC 级使能 */

    TIM2->CR1 |= TIM_CR1_CEN;      /* ③ 启动 */
}

void TIM2_IRQHandler(void)
{
    if (TIM2->SR & TIM_SR_UIF)
    {
        TIM2->SR = ~TIM_SR_UIF;    /* 清标志 */
        g_ms_tick++;               /* 全局毫秒计数 */
        Key_Tick();                /* 按键状态机 */
    }
}
```

中断里再做一个 10 分频，得到 20ms 的采样节拍：

```c
void Key_Tick(void)
{
    static uint8_t Count;
    ...
    Count++;
    if (Count >= 20)               /* 20 × 1ms = 20ms，此刻是真实时间 */
    {
        Count = 0;
        /* 采样 + 状态机 */
    }
}
```

**关键差别**：`Count` 现在数的是**中断次数**，而中断由 84MHz 的硬件时钟驱动。

主循环再慢、再卡、加了 `printf` 还是 Flash 擦除，**采样节拍永远是 20ms**。

### 状态机

```
       按下                  松开              超时(200ms)
 0 ──────────→ 1 ──────────→ 2 ──────────→ 0   （单击）
 空闲        已按下           等双击
            
               按住 2000ms          再次按下
         1 ──────────────→ 4    2 ──────────→ 3  （双击）
          （长按）        长按中      已双击
                           │
                           └─ 每 100ms → 连发事件
```

用五个状态覆盖单击、双击、长按、长按连发四种事件，全部不阻塞。

## 4. 双时间尺度：为什么 `Time` 用 1ms，状态机用 20ms

代码里同时存在两个时间单位，一开始很容易混：

| 变量 | 单位 | 用途 |
|---|---|---|
| `Time[]` | **1ms**（每次中断减 1） | 计时：长按 2000、双击窗口 200、连发间隔 100 |
| `Count` | 1ms（数到 20 清零） | 分频：每 20ms 才采样一次 |

### 为什么不能统一成 20ms

如果 `Time` 也用 20ms 为单位，那长按时长只能是 20 的倍数，`2000ms` 要写成 `100`，而且实际触发时刻误差 ±20ms。这不致命，但没必要。

### 为什么不能统一成 1ms

如果状态机也每 1ms 跑一次，机械抖动（通常 5–10ms）会让一次按键在状态机里被识别成好几次按下/松开。

**1ms 采样会把抖动放大成"多次按键"。** 这就是为什么采样周期必须大于抖动时长。

### 结论

- **`Time` 管"多久"** → 需要毫秒分辨率 → 1ms 单位
- **`Count` 管"什么时候看一眼"** → 需要跨过抖动 → 20ms 节拍

**两个尺度各管一件事，混用任何一个都会出问题。**

代价也很清楚：状态变化的响应延迟最多 20ms。人感知不到，可以接受。

## 5. `volatile` 和临界区：两个都要，各管一半

这是这个模块里唯一一个"不改也能跑、但一定会咬人"的地方。

### 现象

连按 20 次，只响应 18、19 次。偶尔按一下没反应，重按又好了。

### 根因：读-改-写不是原子操作

`Key_Flag[n] &= ~Flag;` 这一行，编译器生成三条指令：

```asm
LDRB   r2, [r0]       ; ① 从内存读一个字节
BIC    r2, r2, r1     ; ② 清掉某一位
STRB   r2, [r0]       ; ③ 写回内存
```

如果中断正好在 ② 和 ③ 之间进来：

```
主循环   LDRB r2 ← 0x00          （读到"没有事件"）
──────────────── TIM2 中断进来 ────────────────
         状态机置位：Key_Flag[0] |= KEY_SINGLE
                   LDRB r3 ← 0x00
                   ORR  r3, #0x08
                   STRB → 0x08     （内存里现在是 0x08，正确）
──────────────── 中断返回 ─────────────────────
主循环   BIC  r2, #0x02           （r2 还是老的 0x00，不知道刚才变了）
         STRB → 0x00               （把 0x08 擦掉了 ✗）
```

**这次按键丢了。**

### 为什么只加 `volatile` 不够

`volatile` 的贡献是：保证那三条指令真的存在，不被优化成寄存器里的值。但它对 ②③ 之间发生的事情**一无所知**。

> **`volatile` 解决编译器优化，不解决原子性。**

### 最终写法

```c
static volatile uint8_t Key_Flag[KEY_COUNT];    /* volatile：禁止编译器缓存 */

uint8_t Key_Check(uint8_t n, uint8_t Flag)
{
    uint32_t pm;
    uint8_t  hit;

    if (n >= KEY_COUNT) return 0;                /* 边界保护 */

    if (!(Key_Flag[n] & Flag)) return 0;         /* 快路径：没事件，不关中断 */

    pm = __get_PRIMASK();                        /* 保存当前中断状态 */
    __disable_irq();
    hit = (Key_Flag[n] & Flag) ? 1 : 0;          /* 慢路径里再确认一次 */
    if (hit && Flag != KEY_HOLD)
        Key_Flag[n] &= (uint8_t)~Flag;
    __set_PRIMASK(pm);                           /* 恢复，不用 __enable_irq() */

    return hit;
}
```

三个设计点：

**① 快路径不关中断**
按键事件是人的速度，99.99% 的调用是"没事件"。开头那个 `if` 让它直接返回，完全不进临界区。（单字节读在 Cortex-M 上是原子的。）

**② 慢路径里再确认一次**
读到有事件、加锁之后再查一遍，避免加锁前被别的东西改掉。

**③ 用保存-恢复，不用 `__enable_irq()`**
`CPSID i` / `CPSIE i` 不支持嵌套。如果写成无脑 `__enable_irq()`，那么"外层已经关了中断"的场景（比如将来 Bootloader 擦写 Flash）会被这一行**意外打开**。

```
进 Flash_Write:  pm=0, PRIMASK=1
  进 Key_Check:   pm=1, PRIMASK=1（本来就关着）
  出 Key_Check:   PRIMASK=1        ← 恢复成 1，没误开 ✓
出 Flash_Write:   PRIMASK=0
```

### 为什么中断那一侧不用加锁

因为 Cortex-M 的抢占是单向的：**中断能抢占线程，线程抢不了中断。**

`Key_Tick()` 在中断里跑的时候，主循环绝对进不来，所以它那边的读-改-写相对主循环是原子的。只有**可能被打断的那一侧**需要保护。

## 6. 三个验证数字

改代码之前测一遍，改完再测一遍，差值就是 bug 的大小。

| 测试 | 改之前 | 改之后 | 验证的是什么 |
|---|---|---|---|
| 秒表 60 秒，数 LED 翻转次数 | — | **60 次** | 1ms 时基准不准（PSC/ARR 算对没有） |
| 连按 50 次单击 | **47～48 次** | **50 次** | 临界区是否真的堵住了竞态 |
| 两个键同时长按 3 秒 | **看似无反应** | **稳定闪烁** | `\|\|` 短路是否漏清标志 |

第二条是核心：**它是唯一能证明竞态被修好的实验。**

改之前少的那 2～3 次，就是第 5 节时序图里被 `STRB` 擦掉的那些位。

## 7. 还没搞清的

留几个真问题，下次接着想：

1. **双击窗口 200ms 是否偏短？** 人手双击间隔的分布大概是什么样？有没有必要调到 250–300ms？
2. **按键数量增加后会怎样？** 现在 2 个键，主循环每轮调用 `Key_Check` 6 次；如果 8 个键就是 24 次，快路径的单字节读是否还够便宜？
3. **长按连发间隔 100ms 合适吗？** 用在"调节参数"场景（比如调 PID 增益）时，人希望多快？
4. **`__get_PRIMASK` 那三行能不能省掉？** 如果改用位带（bit-band）操作，每个位有独立的地址，读写天然原子——但代码更难懂，值不值？
